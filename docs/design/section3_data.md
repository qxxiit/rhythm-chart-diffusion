## 3.3 오디오 전처리

**설계 결정 — 고정 hop STFT 후 비트 격자 보간.**

토큰 격자가 비트 기준이므로 멜 프레임도 비트 기준이어야 한다($1/48$ 비트 간격, 정렬비 $r=4$). 그러나 이를 직접 구현하면 hop 길이가 BPM에 따라, 나아가 변속 곡에서는 구간마다 달라진다. 따라서 2단계로 처리한다.

1. **고정 hop STFT.** 균일한 hop으로 log-Mel을 계산한다.
2. **비트 격자로 보간.** 목표 비트 위치 $b_k = k/48$에 대응하는 시각 $t_k$를 timing point로부터 역산하고(`beat_grid.time_from_global_beat`), 인접 프레임을 선형보간한다.

이 방식은 변속을 자연스럽게 처리하며, 프레임 수가 정확히 $T\cdot r$로 떨어져 §5의 위치별 조건 주입이 성립한다.

**파라미터**

| 항목 | 값 |
|---|---|
| 샘플레이트 | 22,050 Hz |
| n_fft | 512 (23.2 ms) |
| hop (STFT) | 128 samples (5.8 ms) |
| mel bins | 80 |
| fmin / fmax | 30 Hz / 11,025 Hz |
| 스케일 | $\log(x + 10^{-6})$ |
| 정규화 | `[작성] 곡별 정규화 여부 결정` |

`[확인] hop 제약: BPM 216 이상에서는 1/48 비트가 5.8ms보다 짧아져 보간이 업샘플링이 된다. chart_index의 bpm_main 분포에서 216 초과 비율을 확인하고, 유의미하면 hop을 64 samples로 낮출 것.`

**저장.** float16 기준 곡당 약 2.6 MB, 전체 약 50 GB로 추정된다(중앙값 기준). 토큰은 곡당 약 17 KB로 무시할 수준이다. 학습 중 오디오 디코딩을 피하기 위해 전량 사전 계산·캐싱한다.

## 3.4 정합 검증

`[작성] 미실시. 아래는 계획으로 기술하고 §9로 넘길 것.`

두 방식으로 검증한다.

1. **시각 검증.** 스펙트로그램 위에 노트 위치를 오버레이하여 온셋과의 일치를 확인한다(10곡).
2. **수치 검증.** 프레임별 스펙트럴 플럭스와 노트 밀도 시계열의 상호상관을 계산하고, 피크가 lag 0에 있는지 확인한다.

후자가 필요한 이유는 mp3 인코더가 파일 앞부분에 무음 패딩을 삽입하는 경우가 있어 **전곡에 일정한 오프셋**이 발생할 수 있기 때문이다. 이는 시각적으로 발견하기 어려우면서 학습 전체를 무효화한다.

## 3.5 데이터 분할

**분할 단위는 채보가 아니다.** beatmapset당 평균 3.14개의 난이도가 동일 오디오를 공유하므로, 채보 단위로 분할하면 테스트 채보의 오디오가 학습에 이미 등장한다. 모델이 오디오 조건부이므로 이는 직접적인 누수이며 평가 지표를 부풀린다.

**나아가 beatmapset 단위 분할로도 불충분하다.** 동일 곡이 서로 다른 beatmapset으로 중복 업로드된 사례가 **459건**, 이에 영향받는 채보가 **2,779개(전체의 15.06%)** 다.

따라서 **정규화된 artist+title 키로 그룹 분할한다.** 정규화는 대소문자 통일, 괄호 표기 제거, 비문자 제거를 포함한다. 이로써 5,881개 beatmapset이 5,301개 그룹으로 묶인다.

| 분할 | 비율 | 그룹 수 (근사) |
|---|---|---|
| train | 90% | 4,771 |
| val | 5% | 265 |
| test | 5% | 265 |

`[작성] 비율 결정. 평가에 사람 청취가 포함되지 않으므로 test는 작아도 무방하나, §7의 구조 지표가 곡 단위 통계라 최소 규모는 필요.`

**정규화 규칙의 한계.** 괄호 표기를 일괄 제거하므로 "(TV Size)"와 "(Full Ver.)"처럼 실제로는 다른 오디오인 경우도 같은 그룹으로 묶인다(5,881 → 5,301, 580건 병합). 분할 목적에서는 과병합이 안전한 방향이므로 현 단계에서는 유지하며, 규칙 정교화는 §9로 넘긴다.
