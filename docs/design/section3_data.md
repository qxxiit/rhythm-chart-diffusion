## 3.3 오디오 전처리

**설계 결정 — 고정 hop STFT 후 비트 격자 보간.**

토큰 격자가 비트 기준이므로 멜 프레임도 비트 기준이어야 한다($1/48$ 비트 간격, 정렬비 $r=4$). 그러나 이를 직접 구현하면 hop 길이가 BPM에 따라, 나아가 변속 곡에서는 구간마다 달라진다. 따라서 2단계로 처리한다.

1. **고정 hop STFT.** 균일한 hop으로 log-Mel을 계산한다.
2. **셀 격자로 보간.** 토큰과 같은 재원점화 격자(§2.3) 위에서 프레임 시각을 `BeatGrid.frame_times(start_cell, n_cells)`로 얻고(칸당 $r=4$ 프레임, 한 구간 안에서는 1/48비트 간격), 그 시각에서 인접 STFT 프레임을 선형보간한다. `time_from_global_beat`나 따로 재원점화한 1/48 격자를 쓰면 오프비트 red line 뒤에서 칸과 프레임이 어긋난다(§2.3).

이 방식은 변속을 자연스럽게 처리하며, 프레임 수가 정확히 $T\cdot r$로 떨어져 §5의 위치별 조건 주입이 성립한다.

1단계 결과는 **오디오 파일마다** `data/cache/logmel/{audio_id}.npy`(float16, $[n_{\text{frames}},\ 80]$)로 저장하고, 2단계 보간은 창을 읽을 때 한다(`src/data/mel.py`). 한 세트의 난이도들이 오디오를 공유하므로 채보마다 격자 위 mel을 저장하는 것보다 약 2.7배 작고, timing이나 오프셋을 고쳐도 mel을 다시 계산할 필요가 없다. 격자 프레임 $f$의 시각은 `frame_times(r - cell_offset, ...)`이고, 오디오 밖(0 ms 이전, 곡 끝 이후)의 프레임은 무음 값 $\log(10^{-6})$이다. 파일 형식은 `src/data/cache.py` 머리말에 있다.

**디코딩 — 0 ms는 osu!가 정한다.** 채보 시각은 osu!가 재생하는 첫 샘플에서 잰 ms다. osu!는 BASS로 디코딩하고 `BASS_CONFIG_MP3_OLDGAPS`를 켠다(osu-framework `AudioManager`). mp3는 파일 앞에 인코더 지연(LAME 576샘플)과 디코더 지연(529샘플)이 있고, 이를 얼마나 잘라내는지가 디코더마다 달라 최대 1,105샘플(44.1 kHz에서 25 ms) 어긋난다. 합성 파일로 osu!가 쓰는 BASS 2.4.17.48과 비교하면 FFmpeg은 LAME/Lavf/Lavc 외의 인코더 이름과 delay = padding = 0인 태그에서, soundfile은 이름 없는 Xing 태그에서 BASS와 529–1,105샘플 다르다. 그래서 mp3는 FFmpeg의 자체 트리밍을 끄고 디코딩한 뒤(`flags2=+skip_manual`), BASS가 버리는 만큼만 버린다: 이름 첫 바이트가 0이 아니고 delay나 padding이 0이 아닌 LAME 태그면 delay + 529, VBRI 태그면 max(delay, 529) − 프레임 길이, 그 밖에는 0(`src/data/audio.py`). 태그 종류·버전·샘플레이트·ID3·VBRI·ogg를 섞은 합성 파일 37개 모두에서 BASS와 샘플 단위로 일치했다(lag 0). 실제 파일에서의 비교는 `scripts/check_decoder.py --bass`.

**파라미터**

| 항목 | 값 |
|---|---|
| 샘플레이트 | 22,050 Hz |
| n_fft | 512 (23.2 ms) |
| hop (STFT) | 128 samples (5.8 ms) |
| mel bins | 80 |
| fmin / fmax | 30 Hz / 11,025 Hz |
| 스케일 | $\log(x + 10^{-6})$ |
| 정규화 | 곡·밴드별 표준화(평균 0, 표준편차 1, 하한 0.1). 읽을 때 적용 |
| 리샘플링 | soxr HQ (지연 보정, 시각 이동 없음) |

`[확인] hop 제약: BPM 215 이상에서는 1/48 비트가 5.8ms보다 짧아져 보간이 hop 사이를 채운다. 시간 해상도는 hop보다 창(23 ms)이 정하므로 우선 128을 유지한다. scripts/check_alignment.py가 해당 청크 비율을 출력하니, 유의미하면 hop 64를 검토할 것.`

**저장.** float16 기준 오디오 2.5분당 약 4 MB, 전체 약 20–25 GB로 추정된다(채보마다 저장하면 약 55 GB). 토큰은 곡당 약 17 KB로 무시할 수준이다. 학습 중 오디오 디코딩을 피하기 위해 전량 사전 계산·캐싱하고, 격자 보간(창당 약 1.4 ms)만 읽을 때 한다.

## 3.4 정합 검증

**결과(9/27, train 198곡).** 노트 시각 대비 온셋 피크는 전체 중앙값 +18.5 ms(IQR 14.4–21.4)이고, 그룹별로 mp3 lame 18.7 · vorbis 18.3 · mp3 none 17.4 · mp3 xing 16.3 ms로 같다. osu!가 서로 다른 규칙으로 시작점을 잡는 그룹들이 일치하므로 디코딩 규칙은 실제 파일에서도 맞다. 격자 위에서는 +2.86프레임(+20.7 ms)으로 1과 일치한다. 상수 +18.5 ms는 온셋 검출기와 채보 관행의 몫이고, 170 BPM에서 노트 자기 칸의 프레임 4r+2..4r+3에 떨어지므로 전역 시간 이동은 하지 않는다. 곡별 산포(12%가 중앙값에서 10 ms 이상)는 채보마다의 오프셋 차이로 본다.

`scripts/check_alignment.py`가 세 가지를 한다.

1. **수치 검증(오디오).** 곡마다 hop 32(1.45 ms)의 스펙트럴 플럭스를 노트 시작 시각 주변(−60 ~ +60 ms)에서 평균 내고 피크 lag를 잰다. 절대값은 0이 아니다(23 ms 창이 온셋에 닿자마자 플럭스가 오르므로, 무음 속 클릭은 약 −9 ~ −11 ms). 봐야 할 것은 **mp3 태그 종류별(lame / xing / none / vbri, ogg) 피크가 같은가**다. 한 그룹만 약 +12 ms(529샘플)나 +26 ms(1,152샘플) 떨어져 있으면 osu!가 그 파일들의 시작을 `audio.py`의 규칙과 다르게 잡은 것이다.
2. **수치 검증(격자).** 같은 평균을 Dataset이 읽는 그대로의 격자 mel에서 프레임 단위로 잰다. 온셋 프레임이나 그 한 칸 앞에서 피크가 나야 하고, 1과 대략 한 프레임 안에서 맞아야 한다.
3. **시각 검증.** 모델이 보는 격자 mel 위에 노트 행을 그린다(기본 10곡).

합성 데이터(노트마다 클릭을 넣은 mp3)에서 격자 피크는 온셋 프레임 −1에 나오고, 오디오를 5 / 12 / 25 ms 늦게 읽으면 0 / +1 / +3으로 옮겨 간다. `tests/test_pipeline.py`가 정렬(−1 또는 0)과 25 ms 대조군을 매번 확인한다. 25 ms 수준의 전곡 오프셋은 이 검증에서 바로 드러난다.

## 3.5 데이터 분할

**분할 단위는 채보가 아니다.** beatmapset당 평균 3.14개의 난이도가 동일 오디오를 공유하므로, 채보 단위로 분할하면 테스트 채보의 오디오가 학습에 이미 등장한다. 모델이 오디오 조건부이므로 이는 직접적인 누수이며 평가 지표를 부풀린다.

**나아가 beatmapset 단위 분할로도 불충분하다.** 동일 곡이 서로 다른 beatmapset으로 중복 업로드된 사례가 **459건**, 이에 영향받는 채보가 **2,779개(전체의 15.06%)** 다.

따라서 **정규화된 artist+title 키로 그룹 분할한다.** 정규화는 대소문자 통일, 괄호 표기 제거, 비문자 제거를 포함한다. 이로써 5,881개 beatmapset이 5,301개 그룹으로 묶인다.

| 분할 | 비율 | 그룹 수 (근사) |
|---|---|---|
| train | 90% | 4,771 |
| val | 5% | 265 |
| test | 5% | 265 |

배정은 `md5(audio_key)`를 100개 버킷으로 나눠 0–89 / 90–94 / 95–99를 train / val / test로 한다(`scripts/build_manifest.py`). 곡 키만의 함수라서 채보가 추가되거나 순서가 바뀌어도 배정이 달라지지 않는다. 그룹 수는 해시에 따라 위 근사치에서 조금 벗어난다.

`[작성] 비율 결정. 평가에 사람 청취가 포함되지 않으므로 test는 작아도 무방하나, §7의 구조 지표가 곡 단위 통계라 최소 규모는 필요.`

**정규화 규칙의 한계.** 괄호 표기를 일괄 제거하므로 "(TV Size)"와 "(Full Ver.)"처럼 실제로는 다른 오디오인 경우도 같은 그룹으로 묶인다(5,881 → 5,301, 580건 병합). 분할 목적에서는 과병합이 안전한 방향이므로 현 단계에서는 유지하며, 규칙 정교화는 §9로 넘긴다.
